## Практическая работа №7. Две смены одного мастера

### Ответы на контрольные вопросы

1. **Почему два признака `bool` хуже одного перечисления?**
   Два булевых поля (IsCompleted и IsCancelled) образуют 4 комбинации, одна из которых логически невозможна. Кроме того, чтобы отличить открыто от назначено при обоих false, приходится дополнительно проверять третье место - ссылку AssignedHero. Перечисление enum гарантирует, что объект в каждый момент времени находится ровно в одном допустимом состоянии, а компилятор защищает от опечаток.

2. **Какие состояния поручения конечные и почему?**
   Конечными являются состояния Completed и Cancelled. Из них нет исходящих переходов: завершённое дело нельзя отменить или выполнить повторно, а отменённое нельзя назначить или закрыть. Это защищает историю и не позволяет начислить награду дважды или за невыполненную работу.

3. **Куда делась проверка `AssignedHero != null` в `Quest.TryAssign`?**
   Она стала избыточной и заменилась проверкой Status != QuestStatus.Open. По правилам перехода исполнителя назначает только сам метод TryAssign при переходе из Open в Assigned. Следовательно, пока статус равен Open, исполнитель гарантированно равен null.

4. **Где хранится занятость героя?**
   Занятость героя нигде не хранится в виде отдельного поля (в классе Hero нет свойства IsBusy). Она вычисляется методом QuestBoard.IsAssigned(Hero) путём поиска среди всех поручений такого, где одновременно выполняются два условия: quest.Status == QuestStatus.Assigned и quest.AssignedHero == hero. Это исключает рассинхронизацию данных.

5. **Почему проверку занятости нельзя делать после назначения?**
   Если сначала вызвать quest.TryAssign(hero), состояние поручения уже изменится на Assigned, а герой запишется в AssignedHero. Последующая проверка IsAssigned(hero) увидит это же самое поручение, вернёт true, и метод QuestBoard.TryAssign вернёт ложный отказ, хотя изменение в объекте уже произошло. Проверка должна идти строго до любых изменений.

6. **Почему доска не даёт удалить Сергея?**
   Потому что в списке поручений доски есть карточки (№101, №102, №103), в которых свойство AssignedHero ссылается на объект Сергей. Метод QuestBoard.TryRemoveMember запрещает удаление героя при наличии любой ссылки на него, чтобы история дел не вела в пустоту на несуществующего участника гильдии.

### Разбор двух ошибок

**Ошибка 1 (Занят навсегда):** Если из IsAssigned убрать проверку quest.Status == QuestStatus.Assigned и оставить только quest.AssignedHero == hero, то после завершения №101 ссылка на Сергея остаётся в карточке для истории. Доска начинает считать Сергея вечно занятым старым выполненным делом и отказывает в назначении на №102 (False).
**Ошибка 2 (Сначала назначили, потом спросили):** При вызове quest.TryAssign(hero) до проверки IsAssigned(hero) поручение сразу переходит в статус Assigned. Затем проверка IsAssigned(hero) находит это же назначенное поручение и возвращает true, из-за чего метод возвращает false. В результате метод отвечает отказом, но само поручение остаётся назначенным.

### Самостоятельный шаг

**CountByStatus(QuestStatus status):** проходится циклом по _quests, подсчитывает количество поручений с совпадающим Status и возвращает счётчик, не меняя состояние объектов.
**FindActiveQuest(string heroName):** находит героя в гильдии по имени (если не найден - возвращает null), затем ищет в _quests поручение со статусом QuestStatus.Assigned и этим героем в AssignedHero. Если такого нет - возвращает null.
**IsAssigned в одну строку:** да, после добавления FindActiveQuest метод IsAssigned можно переписать в одну строку:
csharp public bool IsAssigned(Hero hero) => FindActiveQuest(hero.Name) != null;

### Личный проект: Каталог игр и сессии обзоров (ReviewSession/ReviewBoard)

Для операции оценки игры (ReviewSession) введено перечисление ReviewStatus со значениями Open, InProgress, Completed, Cancelled.

#### Таблица переходов `ReviewStatus`

|Текущее состояние|TryStart|TryFinish|TryCancel|
|:---|:---:|:---:|:---:|
|**Open**(открыта)|InProgress|отказ(false)|Cancelled|
|**InProgress**(в работе)|отказ(false)|Completed|Cancelled|
|**Completed**(завершена)|отказ(false)|отказ(false)|отказ(false)|
|**Cancelled**(отменена)|отказ(false)|отказ(false)|отказ(false)|

**Конечные состояния:** Completed и Cancelled. Из них нельзя возобновить обзор, повторно обновить рейтинг игры или отменить уже завершённую сессию.
**Почему занятость вычисляется, а не хранится:** В класс Game не добавлялось поле IsUnderReview. Занятость игры вычисляется методом ReviewBoard.IsUnderReview(Game) по наличию сессии в статусе ReviewStatus.InProgress для данной игры. Это гарантирует, что игра не зависнет в состоянии вечного обзора при добавлении новых способов отмены или завершения сессий, а также не требует дублирования состояния в двух классах.
**Защита истории:** Метод ReviewBoard.TryRemoveGame запрещает удалять игру из GameCatalog, если на неё ссылается хотя бы одна сессия обзора.

### Дополнительная часть

**Д.1. История героя (GetQuestsOf):** при получении всей истории поручений героя состояние не проверяется, потому что нам важен сам факт участия героя в деле - будь оно текущим (Assigned), успешно завершённым (Completed) или отменённым (Cancelled). Для вычисления занятости (IsAssigned), напротив, нужно учитывать только активную работу в текущий момент (Status == QuestStatus.Assigned).
**Д.2. Значение, которого нет ((QuestStatus)7):** при выводе strange в консоль печатается число 7, так как в C# перечисление (enum) под капотом является целым числом (int), и явное приведение типа (QuestStatus)7 пропускает любое числовое значение, даже не объявленное в списке. Ветка default в GetStatusText() необходима по двум причинам: компилятор требует гарантированного возврата строки при любом возможном значении базового типа int, а сама программа остаётся защищённой от некорректных данных.
